One card per error code from TSD §6.2. Each includes: icon, code, user message, "what to do next", and action CTA.

INTERNAL_ERROR is the catch-all. The actual error IS logged server-side (job_events.detail) but never exposed to the user (PRD §6.1: "No stack traces or server state in user-facing errors. Ever."). This card is the design pattern for that requirement.
Error card placement: Error cards appear inline on the Job Progress page — replacing the current stage entry when it fails. The full stage machine stays visible above the error card so the user can see which stage failed. The "Try again" / "Try different URL" CTAs navigate back to the Submit screen with the URL pre-filled where appropriate.

No stack traces rule: enforced by: (1) this design never rendering internal details, (2) a CI integration test that asserts no stderr or stack trace appears in any API response body (TSD §9).

Error Pattern Rules

  • Every error = icon + code label + title + message + next steps + CTA
  • Code label shown (e.g. DOWNLOAD_BLOCKED) for devtools, not primary copy
  • Message: plain English, no jargon, no internal details
  • "What to do next" is always present — never a dead end
  • Primary CTA always actionable (retry, try different URL, etc.)

Error Placement in App

  • Errors replace the active stage on the Progress screen (inline)
  • Stage machine stays visible above — shows which stage failed
  • DOWNLOAD_INVALID_URL: shown inline below URL input on Submit screen
  • Navigation: "Try different URL" → Submit screen, URL cleared
  • "Retry" → re-queues same URL (POST /api/jobs with same params)

Security Requirements

  • INTERNAL_ERROR: logged server-side, never detailed to user
  • No stderr, no stack traces, no file paths in any response
  • CI integration test enforces no-stack-trace rule per TSD §9
  • Error codes are typed (enum) — no free-text exceptions surface
  • All 9 error codes have a triggering integration test (TSD T30)
