# Test-only dependencies. NOT installed into the production worker image (Dockerfile
# installs requirements.txt only). Install with the same constraints as the main file:
#   pip install -r requirements.txt -r requirements-dev.txt -c constraints-prod.txt
# (`make install` and the CI "Tests" job do this.)
#
# WHY THIS SPLIT EXISTS, AND WHY IT IS PARTIAL. moto is a library whose whole purpose is
# to impersonate AWS S3; it does not belong in the process that talks to real R2, so it
# lives here. But ruff, black, pytest and pytest-asyncio are ALSO test/dev tools and are
# still in requirements.txt, hence in the production image. That is pre-existing debt,
# deliberately not moved in the PR that introduced this file (moving them risks the image
# build). Move them here when someone can verify a worker image build.
#
# tests/real_r2.py needs moto to run the retention sweep against a real S3 server. Without
# it those tests SKIP locally with a named reason, and FAIL when CI=true.
#
# WHY moto IS PINNED EXACTLY, unlike the floors in requirements.txt. This is a REQUIRED
# check, and the harness reaches into moto's internals to back-date an object (S3 has no
# API for that): `s3_backends[...].buckets[...].keys[key].last_modified`. A moto release
# that moves them would turn `Tests` red on every PR, with no change on the PR to blame.
# It would be red, not silently green (real_r2.RealR2.age reads each age back through the
# real list call), but red on everyone is still an outage. Bump it on purpose, in a PR
# that runs the retention tests.
#
# WHAT THE PIN DOES NOT COVER. moto's own dependencies (Flask, Werkzeug, responses,
# cryptography, ...: 38 further packages in a clean dry run) still resolve to whatever is
# newest, because constraints-prod.txt describes the production image and moto is not in
# it. Freezing those needs a separate constraints file generated from a known-good install.
moto[s3,server]==5.2.5
