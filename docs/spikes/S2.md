## ⚠️ Architectural flag (this is the real open question, not "does pg-boss work")
pg-boss is a **Node.js** library. The producer (Next.js API route) is Node and uses pg-boss natively, **but the consumer (`apps/worker`) is Python** and cannot call pg-boss directly. Two ways to reconcile:
- **(a)** Python worker polls the `pgboss.job` table via `SELECT … FOR UPDATE SKIP LOCKED`, while pg-boss still owns enqueue/retry/scheduling semantics on the producer side. *(recommended)*
- **(b)** A thin Node consumer process owns the queue and RPC/shells into the Python pipeline.

The poison-isolation + connection-budget result above holds **either way**.

## Developer recommendation
**Confirm pg-boss** for enqueue + retry + scheduled-job semantics, with the **Python worker consuming via `FOR UPDATE SKIP LOCKED` on `pgboss.job`** (option (a)). One durable Postgres-native queue, no Redis (anti-goal #7), Python worker boundary respected.
