# S1 — Decision Record: YouTube Download Path Bake-off

- **Spike:** TSD §8 / S1 · Component C4 · de-risks R1 (the #1 risk)
- **Success criterion (Gate 0):** chosen path ≥95% success across 50 representative URLs; p90 fetch <10s. Prefer lower operational burden when both pass.
- **Date run:** 2026-06-30 · **Status:** architecture recommended; **headline metric NOT measurable in this environment** (see Blockers).

## What was exercised
Two download paths were stood up as the smallest possible experiment — no UI, no queue:
- **Cobalt** (self-hosted, Fly): `spikes/s1_bakeoff/cobalt_client.py` + deploy spec `cobalt/Dockerfile` + `cobalt/fly.toml` (scale-to-zero). Sidesteps cookies entirely (satisfies anti-goal #1).
- **yt-dlp + server-managed cookie rotation:** `spikes/s1_bakeoff/ytdlp_client.py`. Cookie pool is server-side only; cookie/token material redacted from captured stderr.
- **Harness:** `spikes/s1_bakeoff/harness.py` — runs N URLs through both concurrently, reports per-path success rate + p90 latency to `s1_results.csv`.

**Robustness confirmed:** both clients return a measured dict and never raise — the harness can score a full run unattended.

## Blockers — why the ≥95% / p90 metric cannot be measured here (honest)
1. **Cobalt not deployed** — no `fly`/`flyctl` CLI or Fly.io account in this sandbox.
2. **No `yt-dlp` binary + no `ffmpeg`** on PATH — `-x --audio-format wav` cannot transcode.
3. **Only 1 of 50 URLs provided** — `fixtures/fixture_urls.txt` has the Gate 2 demo URL only; the 50-URL set is operator-provided.
4. **Datacenter IP** — sandbox egress is bot-challenged by YouTube, so any number measured here would *understate* the real (Fly/residential) rate. This is the exact V1 failure mode the spike exists to neutralise.

## Developer recommendation (pre-measurement)
Lean **Cobalt primary + yt-dlp fallback.** Cobalt removes cookie-pool maintenance (anti-goal #1) and the dual-path design keeps yt-dlp as a resilient fallback. Lower operational burden wins the tie-break if both clear the bar.
