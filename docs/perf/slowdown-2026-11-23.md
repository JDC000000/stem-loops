# Slow-down (Phase C C1, Beta): perf and sync, 2026-11-23

Agent C-1, session 19B. Engine: `apps/web/src/lib/play/engine.ts` + `stretch.ts` at the PR head. Raw data:
`slowdown-2026-11-23.json`. Harness: `slowdown-harness/` (`harness.ts` drives the REAL engine and the REAL SoundTouch
provider; `driver.mjs` runs headless Chrome; `analyze.py` computes the tables).

## Set-up
- One headless Chrome (v153), 390×844 mobile viewport, **4× CDP CPU throttle**, 24 kHz decode (the phone path).
- Song: the C0 spike's synthetic 6 stems, 300 s, Opus 128k. Every stem carries the same 4 ms marker every 5 s, so a
  probe worklet on each stem's gain timestamps when each stem's marker is **heard** (to the sample).
- Each real-time run plays 5 min at the reduced speed with this script: first switch from 100% (builds and warms the
  six nodes), seek, pause/play, seek, 100% and back, seek, section loop on/off, switch to the other speed and back,
  seek, pause/play, seek, 100% and back. 18 events per run.
- **Box load (uptime): 3.9–7.6 on 2 cores during every run.** The < 3 target never came; runs were made anyway.
  0.75: before 6.66 6.41 6.88, after 3.86 4.95 6.14. 0.9: before 7.62 7.47 7.37, after 6.85 6.44 6.91.
  CPU and underrun figures are therefore pessimistic.
- The 4× throttle slows the main thread, not the audio render thread: worklet cost is desktop-x86 cost. A real phone
  is still needed (REAL-DEVICE-CHECKLIST).

**The 90% outliers are not misalignment.** In all three, the keys stem has TWO onsets: an early copy ~90–100 ms
before the true one, and the true one aligned with the other five stems within 21 ms (raw onsets, e.g. t=100.51:
keys at 100.510 and 100.595, others 100.595–100.614). That is a WSOLA duplicated transient (pre-echo) on one stem:
audible as a **flam**, which is exactly what Jon's listening test must judge. The 75% run had none this time; an
earlier 75% run on the same build (no raw onsets saved) showed the same keys signature twice (−96 / −125 ms).

**G2 sign:** negative = the playhead is slightly BEHIND what is heard (chords ~10 ms late at most medians, never more
than 24 ms). At 100% the same measurement reads +0.9 ms. Within the ±50 ms target with room; no tuning done.

**Superseded run (kept in the JSON):** the first 75% run on an earlier build had a 114 ms spread on the first marker
after a 75→90 switch. Cause: the new run's `cancelScheduledValues` cancelled the stop fade-out, so the OLD run's tail,
still draining out of the stretch pipeline, was heard at full gain. Fixed (the fade is held until the new run is
heard; test `G2 @…: the fade-out is not cancelled before the new run is heard`, mutant M6). After the fix, the first
marker after every one of the 36 events in the two runs is ≤ 34 ms (ignoring the keys duplicate).
