## 1 · Merging (rewritten in v3.5; D-7 folded in v3.6; gate v3.6 wording in v3.6.1)

**M-SA. Self-approval.** The canonical text is **AGENTS.md M-8, "M-SA"**; this section summarises it and must not diverge. The orchestrator (main session only; subagents never merge) merges a PR without asking Jon when ALL hold:
1. **Review:** a dispatched reviewer agent on a different model from the author wrote a review file with exactly one `VERDICT: PASS <91-100> HEAD <sha7>` line at the reviewed SHA, and ran the tests and ≥ 3 mutants. The orchestrator never writes, edits or converts a review file; the author's agent never reviews.
2. **Second reviewer** (third model, PASS > 90, same content) for **every PR in the gate's protected class**: a path matching `PROTECTED_RE` in `scripts/or4-merge.sh`, the label `needs-jon-approval`, or a `[billing]` title. Money-class PRs (condition 6) always need this second reviewer, protected path or not, and both reviews must score ≥ 93. The merge path (`scripts/or4-merge.sh`, `scripts/test_or4_merge.py`, workflows, CODEOWNERS, `.claude/settings.json`, rulesets, AGENTS.md M-SA, this §1) is inside that class.
3. **Gate:** `scripts/or4-merge.sh` ≥ v3.6, invoked `or4-merge.sh <pr> <review-file> <reviewed-sha> [<review-file-2>]` (the 4th argument, the second review file, is required for a protected or money-class PR), `DRY_RUN=1` first (only the literal `1`; issue #391), then the real run with `JON_ROW=95 JON_PR=<pr>` (D-6 standing row; JON_PR ties each run to one PR). A PR implementing a JON row that changes these rules runs with that row instead (see HELD below).
4. **CI** green on the PR head; protected PRs behind 0; others may use `ALLOW_BEHIND=1` (≤ 5, disjoint, no coupled/hot files). **Rule 9b:** if the PR content changed after review (not just an `update-branch`, which the patch-id check passes), a non-author agent writes a delta review at the new head first.
5. **Migrations:** a PR that adds a migration, or code depending on an unapplied one, merges only AFTER Jon has applied it to prod and staging and both DBs are verified (one bare SELECT each). A `DROP` migration goes to Jon as a file first. Hold without a merge question until his apply is on the ledger.
6. **Money class (D-7, from SA-2):** a PR touching billing, Stripe, credits, entitlements, auth or sessions, the service-role key, secret handling, RLS / grants / roles, webhooks, job creation or admission, uploads, retention, spend (Replicate, Klangio) or pricing copy, or with a `[billing]` title. When in doubt, money class. A money-class PR is treated as protected whether or not a path matches `PROTECTED_RE`: it always needs the second reviewer on a third model (condition 2), must be 0 behind (`ALLOW_BEHIND` is never used), and is run with `JON_ROW=95 JON_PR=<pr>`. Gate v3.6 classifies money by `MONEY_RE` plus a `[billing]` title, but that regex is a floor, not the classification: it still misses some money paths (e.g. `api/library/remake/route.ts`, worker `reaper.py` and `consumer.py`, `stem-urls.ts`, account pages, `lib/db.ts`, account deletion, job failure and retry; #406). The orchestrator always classifies by reading the changed-file list, sets `MONEY=1` for the gate run whenever the regex does not match but the PR could be money class (when in doubt, `MONEY=1`; it may only raise the class), sets `MONEY=1` for any non-ASCII path, and records the class in the ledger row before the real run. Each review's first line is `VERDICT: PASS <93-100> HEAD <sha7>` and its **line 2** is exactly `SCORES: M-9 <n> M-11 <n>`, both ≥ 93; report min(M-9, M-11) in the ledger row. Free-text or table-only scores: the orchestrator treats the review as not passed (gate v3.6 also refuses them). Where the changed path has real-Postgres CI tests ("Tests", "Worker tests (PG 17 = production parity)", "RLS gate"), they ran and passed at the PR head, re-read from the GitHub job log; where it has none, the review says so in one line. Every finding not fixed is listed under a non-empty "Residue" heading in the PR body, with an issue number for follow-up work; listing residue never substitutes for the ≥ 93 bar (residue below the bar is accepted only by Jon, M-11). This is D-7's exception to M-9's no-score rule, for money class only. A money-class PR that also adds a migration follows condition 5 as well.
7. **Class D, device- or listening-gated (D-7):** this adds no merge route. Conditions 1–6 must all hold first; class D only lets Jon's device or listening check come after the merge instead of before it. It applies only when (a) that check is the single open item, (b) the PR is not money class, not in the protected class and carries no migration, and (c) the review file states, naming the test or flag as evidence, one of: the feature is default-off behind a flag Jon can leave off; the changed code path is not reached on any device or browser outside the named target set; or the feature ships behind a Beta label that a JON ledger row named for that feature (the review cites that row number and the orchestrator verifies it against the ledger before merging). The reviewer makes that statement, never the author or the orchestrator; without it the PR waits for Jon's check. Log each class-D merge as "class D, awaiting Jon"; ask Jon for his result at the start of the next cycle; at most 3 class-D merges may await a result at once. **The merging orchestrator (or its successor session) owns the revert:** a failed check means a revert PR, or a PR that turns the flag off, opened within one cycle and merged through the same M-SA path.

**Enforced by the gate (code, v3.6):** a PASS marker at the reviewed SHA, exactly one `VERDICT:` line and it is line 1; protected and money PRs: two review files (4th arg) with valid markers, different paths, not identical after whitespace normalisation; money class (`MONEY_RE` path, `[billing]` title or `MONEY=1`): marker score ≥ 93 and `SCORES: M-9 <n> M-11 <n>` (n 93-100) as the only SCORES line, on line 2, and money implies protected; a protected class needs a numeric `JON_ROW` + `JON_PR` equal to the PR, behind 0 (`ALLOW_BEHIND` never); patch-id equality, not draft, ≥ 10 green check-runs and statuses, behind rules, no merge-bot labels.
**Process (orchestrator duty, not enforced):** reviewer model ≠ author, real independence of the two reviews (the duplicate check is byte-level after whitespace normalisation, not proof of independence; an edited copy can pass it), tests/mutants ran, the review was written by a reviewer agent, `DRY_RUN=1` first, main session only, the row is 95 (or the JON row for a rules PR; the gate accepts any numeric row), and for a rules PR the ledger row really names this change; the gate accepts a single review at 91 for a money PR its regex misses, but only when the PR is also outside the protected class (otherwise it demands two files), unless `MONEY=1` is set, so the orchestrator sets it; money classification beyond the regex (including setting `MONEY=1`); the real-Postgres log check; the Residue heading; the marker score matching min(M-9, M-11); a later indented or reworded `VERDICT: FAIL` or lower `SCORES` line is not counted by the gate, so read the whole review; class D eligibility and the Beta row; the worker deploy and its health check; the FYI line. The gate cannot verify the ledger row, reviewer identity or model, or that the reviews are independent. Before the real run, log both review files, models and scores. Never call a process item "checked by the gate".

**HELD for Jon, a control change not a merge ask:** a PR that removes or loosens a gate check, changes M-SA / this approval rule, CODEOWNERS, `.claude/settings.json`, rulesets, or the merge logic of workflows (`auto-merge.yml`, autonomy-class, the labellers). A PR implementing a JON row that changes these rules runs the gate with `JON_ROW=<that row>`, never 95, and contains only what that row names. The orchestrator does not self-merge a HELD PR (the list in the first sentence): it puts one line in the cycle brief and waits for a JON row naming that change. Tightening-only changes may be self-approved with two reviewers.

**Hard-rule items (never merge approvals; still Jon's):** applying a migration to prod/staging, any `DROP` migration, Stripe live mode and any Stripe price, product or dashboard change, secrets/tokens/env, paid-API budgets and any other spending, ruleset or repo-settings changes, deleting R2 data, any write to the prod or staging database (agents read only), irreversible or not, and anything a classifier or permission system refused (OR-1: never re-route).

**After every self-approved merge:** log the ledger row (PR, reviewers + models + scores, gate version, merge SHA); watch `v3/main` CI at the merge SHA. If `v3/main` goes red because of the merge: all merges stop (M-5), and a revert PR is opened, reviewed and self-merged under M-SA (a revert of a PR that carried an applied migration is held for Jon: code and schema must be reconciled by him). Report merges to Jon in the cycle summary (no question). **Worker deploy (D-7; SA-2 v1.2.1 §4, LEDGER-19A row 110):** the orchestrator (main session) dispatches it under M-SA (D-7); subagents never do. After a merged PR that changes `apps/worker/**`, and only once `v3/main` CI is green at the head being deployed (the merge SHA or later) and no migration the worker code depends on is unapplied (condition 5), dispatch `deploy.yml` once with `target=worker` and `ref=v3/main` (never `all` or `web`, never another ref), in the foreground (never an unattended background script), batching worker merges within ~30 min. Then confirm the "Deploy Worker to Fly.io" job succeeded and `https://stem-loops.fly.dev/health` is ok with the fetch canary ok within 10 min. Web deploys, Fly secrets, scaling, volumes and `fly.toml` stay Jon's. A refused dispatch is OR-1: record it, tell Jon, do not re-route (no `make deploy-worker`, no `flyctl`). If health fails: stop all merges (M-5), tell Jon at once, and open a pure `git revert` PR of the merge commit (a revert of a PR that carried an applied migration is held for Jon, because code and schema must be reconciled by him); it goes through the same M-SA path as any PR (gate, CI green, and for a protected or money-class original the same reviewers and score bar; the reviews confirm it is an exact revert); after it merges, redeploy once and re-check `/health`. **FYI (D-7):** right after each merge, write Jon one line in the session's reply (PR, class, review scores, residue issue or "none", how to revert) and repeat it in the cycle summary. It is information, never a question.

**Stop and tell Jon (not a merge ask) when:** a reviewer FAILs the same PR 3 times; reviewers disagree across models by > 15 points; a classifier/permission/proxy refusal (OR-1). A gate-loosening PR is HELD (above), not merged.

**Removed in v3.5:** v3.4.3's "never skip or run ahead of a human gate" now means the HELD and hard-rule items; "protected PRs need Jon's named per-PR approval"; batching merge questions into decision briefs; the D-1(i) non-protected-only scope.

## 2 · Work rules (carried from v3.4.2, updated)

1. **Split, then label** PARALLEL / SERIAL; > 5 tasks → file-ownership table before dispatch.
2. **Two sessions.** The A session (19A, 20A, …) owns `.github/**`, `scripts/**`, `.claude/**`, `docs/agentic*`; the B session owns `apps/**`, `packages/**`, product docs. Cross-paths only via an issue. Chromium (2) and git-network (2) caps are shared: 1 each per session unless a hand-off is logged. **One merge gate** for both sessions (v3.6 today; #390, #395); never fork a private gate copy — propose changes as a PR (lesson: #382 vs #385 diverged).
3. **One agent, one task, one worktree, one branch.** The orchestrator creates the worktree and names its path in the brief; the agent works only there. Six agent files set `isolation: worktree` (roster below). Per the Claude Code docs that gives the agent a temporary worktree branched from the repo's default branch (not the PR branch, not the parent's `HEAD`), removed if unchanged; earlier sessions also saw the platform refuse it. Either way it is never the task worktree: the brief's path wins, and work left only in the isolation worktree does not count. Brief = goal, files, done-definition, output path, COMMON-RULES pointer, turn budget. Agents reply ≤ 10 lines.
4. **Agent types:** the roster is the table below (the agent files in `.claude/agents/` are the source of truth for each field; `docs/agent-registry.md` maps the old registry names to it). All 8 passed the O-6 smoke test as real subagent types (`developer`, `release-ops` in S19; the other six in S21A, #389 comment of 2026-11-24), so dispatch the named type, not `general-purpose`.

   | Agent | Model (default) | Tools (frontmatter) | May write | `isolation` | `maxTurns` | Use for |
   |---|---|---|---|---|---|---|
   | `orchestrator` | sonnet | Read, Grep, Glob, Bash, Write, Agent, TodoWrite | ledger / handover files outside the repo (rule 13); never code, reviews or docs | — (main session) | 120 | split, dispatch, check proof, M-SA merges |
   | `task-splitter` | sonnet | Read, Grep, Glob, Bash, Write | its ticket list only | — | 40 | phase or > 5 tickets → PARALLEL/SERIAL tickets |
   | `developer` | opus (sonnet for routine) | Read, Write, Edit, Bash, Glob, Grep, TodoWrite | code, tests, docs in its worktree; push its branch, open a draft PR | worktree | 80 | implementation |
   | `tester` | sonnet | Read, Write, Edit, Bash, Glob, Grep | tests in its worktree | worktree | 60 | write / repair tests |
   | `code-reviewer` | sonnet (any model ≠ author) | Read, Grep, Glob, Bash; `disallowedTools` Write, Edit, NotebookEdit, Agent | its review file only (via shell redirect); no git or GitHub writes, enforced by a PreToolUse hook (`scripts/agent_readonly_guard.py`) | worktree | 40 | adversarial review, tests + ≥ 3 mutants |
   | `security` | sonnet | same as `code-reviewer`, same hook | its findings file only; no git or GitHub writes (hook) | worktree | 50 | security audit, money-class second lens |
   | `release-ops` | sonnet | Read, Grep, Glob, Bash | evidence packets; no merges, labels or workflow edits (prose rule, no hook) | worktree | 60 | merge-evidence packets, CI triage, deploy checks |
   | `batch-runner` | haiku | Read, Grep, Glob, Bash, Edit | bulk edits in files the brief names; no git writes | worktree | 30 | mechanical batches, inventories |
5. **Hot files and money:** one writer at a time for migrations, generated files, lockfiles, shared config, AGENTS.md. No paid APIs without Jon's budget. After any Jon DB step verify **both** DBs.
6. **Model per task:** haiku (sweeps), sonnet (routine code/docs), opus (money, security, cross-stack, synthesis), fable (safety-critical second review).
7. **Check the proof yourself:** PR exists, diff non-empty, CI on the head SHA, gate evidence re-read from GitHub. Review markers are checked verbatim; never convert a malformed score (lesson: `PASS 9/10`).
8. **Review:** author ≠ reviewer model; PASS > 90 (money class: the ≥ 93 bar of §1 condition 6, D-7); max 3 rounds per PR, then stop and report. Residue the PR admits → an issue. Reviewers get the previous round's harness; authors pre-run it.
9. **No label-based auto-merge, ever** (D-2; §11 R1 stopped after 4 failed reviews). Rebase only with `PUT …/update-branch` (D-3).
10. **Concurrency:** ≥ 5 agents when there is work, cap 10; background CI waits, no polling check-ins. Don't loop update-branch while another session merges: use `ALLOW_BEHIND=1` where eligible, else update once right before merge.
11. **Jon's attention:** one batched brief per cycle, only for decisions that are really his (hard-rule items in M-SA 5, product calls, refusals). Never re-ask what is approved. **Never ask for a merge.**
12. **Stop rules:** second failure of the same task → stop and report; near usage limit → no new agents; heavy context → write the handover.
13. **Measure every cycle** in the Project ledger: agents, models, merges, review rounds/scores, refusals, Jon asks (target: 0 merge asks), unlock line. Session notes never go into the repo; that includes the orchestrator's cycle log (`.claude/agents/orchestrator.md` step 6 writes it to the Project ledger, never `claude/cycles/`).
